# Лабораторна робота №7. IPC (Pipes), Redirection, Signals та Mini-Shell

## 1. Мета роботи
Інтегрувати ключові абстракції операційної системи (`fork()`, `execvp()`, `waitpid()`, `pipe()`, `dup2()`, `open()`, `close()` та `sigaction()`) і створити власний інтерактивний командний інтерпретатор (`mini_shell.c`) з підтримкою вбудованих команд, перенаправлення виводу (`>`), конвеєра (`|`) та обробки сигналів (`SIGINT`).

---

## 2. Частина I. Pipes (Анонімні канали)

### Завдання 1. Створення Pipe (`pipe_basic.c`)
- **Результат запуску:** `Read end: 3`, `Write end: 4`, `Received: Hello through pipe!`.
- **Чи є pipe звичайним файлом?** Ні, це буфер у пам'яті ядра (FIFO-черга байтів), який не має імені у файловій системі.
- **Чому до pipe можна застосовувати `read()` і `write()`?** Завдяки уніфікованій абстракції файлових дескрипторів POSIX (*everything is a file descriptor*).
- **Чому `pipe()` повертає два файлові дескриптори?** Канал є односпрямованим потоком даних: `pipefd(0)` призначений виключно для читання (*read end*), а `pipefd(1)` — для запису (*write end*).

### Завдання 2 та 3. Pipe між процесами (`pipe_processes.c`), `pipe_no_close.c` та `strace`
**Карта дескрипторів після `fork()` та після закриття зайвих кінців:**
```text
Одразу після fork():                 Після конфігурації:
Parent             Child             Parent ──(write fd 4)──► PIPE ──(read fd 3)──► Child
fd 3 → Read        fd 3 → Read       (fd 3 закрито)                                 (fd 4 закрито)
fd 4 → Write       fd 4 → Write
```
- **Результат `pipe_processes`:** `Child received: Message from parent`.
- **Експеримент без `close()` (`pipe_no_close.c`):** Якщо `parent` (або сам `child`) залишає відкритим дескриптор запису (`write end`), системний виклик `read()` у `child` після вичитування всіх даних **блокується назавжди** замість повернення `0` (EOF). Порожній канал ще не означає кінець потоку — EOF виникає лише тоді, коли **канал порожній І закриті всі дескриптори запису**.
- **Аналіз `strace`:** Трасування (`pipe2` → `clone` → `close` → `write(4, ...)` → `read(3, ...)` → `read(3, ...) = 0` → `close` → `wait4`) підтверджує синхронізацію читання/запису через ядро.

## 3. Частина II. Redirection (`dup2`) та Pipeline

### Завдання 4 та 5. `dup2()` (`dup2_output.c`) та `exec()` + Redirection (`redirect_exec.c`)
**Зміна таблиці дескрипторів при `dup2(fd, STDOUT_FILENO)`:**
```text
До dup2():                 Після dup2(fd, 1):           Після close(fd):
fd 1 → Terminal            fd 1 ──┐                     fd 1 → redirected.txt
fd 3 → redirected.txt      fd 3 ──┴──► redirected.txt   (fd 3 закрито)
```
- Після виклику `dup2()` стандартний вивід (`fd 1`) вказує на файл `redirected.txt` (або `ls-output.txt` у `redirect_exec.c`). При виконанні `execvp("ls", ...)` таблиця відкритих файлових дескрипторів зберігається, тому `ls -l` записує результат у файл, не знаючи про перенаправлення.

### Завдання 6. Конвеєр `ls -l | wc -l` (`pipeline.c`)
**Схема взаємодії процесів та дескрипторів:**
```text
Child 1 (ls -l) ──[fd 1 → pipe write]──► PIPE ──[pipe read → fd 0]──► Child 2 (wc -l)
```
- `Child 1` перенаправляє `STDOUT_FILENO` у `pipefd(1)` і закриває обидва кінці каналу.
- `Child 2` перенаправляє `STDIN_FILENO` на `pipefd(0)` і закриває обидва кінці каналу.
- `Parent` обов'язково закриває обидва дескриптори каналу до виклику `waitpid()`, щоб `wc -l` отримав EOF одразу після завершення `ls -l`.

## 4. Частина III. Signals (`signal_int.c`, `signal_parent_child.c`)
- **Чому в `handle_sigint()` використовується `write()`, а не `printf()`?** Сигнал надходить асинхронно і може перервати виконання не-реентерабельної функції `stdio` (яка утримує внутрішні блокування). У обробнику сигналів дозволені лише **async-signal-safe** системні виклики (`write()`).
- **Поведінка `signal_parent_child.c`:** із `SIG_DFL` виклик `kill(pid, SIGTERM)` негайно завершує дочірній процес сигналом; із власним обробником через `sigaction()` процес перехоплює сигнал і виходить коректно (`status 0`).
- **Різниця між `SIGINT`, `SIGTERM` та `SIGKILL`:** `SIGINT` (2) — переривання з клавіатури (`Ctrl+C`), можна перехопити; `SIGTERM` (15) — запит на коректне завершення, можна перехопити; `SIGKILL` (9) — безумовне знищення процесу ядром, неможливо перехопити чи ігнорувати.

## 5. Частина IV. Mini-Shell (`mini_shell.c`)
1. **Чому `cd` та `exit` реалізовані як built-in (без `fork()`)?** Робочий каталог (`cwd`) є атрибутом процесу: виклик `chdir()` у дочірньому процесі змінить каталог лише дитини, яка одразу завершиться, а батьківський `mini_shell` залишиться у старій директорії. Аналогічно `exit` має завершувати цикл самого `mini_shell`.
2. **Результати тестів:** `pwd` → `cd /tmp` → `pwd` підтвердив зміну каталогу; `echo test > /tmp/ms_test.txt` перенаправив `stdout` у файл через `open()` + `dup2()`; `ls -l | wc -l` об'єднав процеси через `pipe()` + `dup2()`; `Ctrl+C` (`SIGINT`) перериває фонову команду (`SIG_DFL`), тоді як `mini_shell` (`SIG_IGN`) продовжує роботу.
3. **Трасування `strace -f` для `mini_shell`:** `clone()` створює дочірні процеси, `openat()` відкриває файл перенаправлення (`fd 3`), `pipe2()` створює канал (`fd 3, 4`), `dup2(3, 1)` та `dup2(3, 0)` підміняють `stdout`/`stdin`, після чого `execve()` запускає цільові утиліти (`echo`, `ls`, `wc`).

## 6. Відповіді на контрольні питання
1. **Що таке IPC?** *Inter-Process Communication* — механізми ядра ОС для обміну даними та синхронізації між процесами (pipes, сигнали, сокети, спільна пам'ять).
2. **Що створює `pipe()`?** Анонімний односпрямований канал у буфері ядра та два дескриптори: для читання і для запису.
3. **Що означає `pipefd`?** Дескриптор кінця каналу для читання (**read end**).
4. **Що означає `pipefd`?** Дескриптор кінця каналу для запису (**write end**).
5. **Чому pipe можна використовувати через `read()` та `write()`?** Завдяки моделі UNIX/POSIX «усе є файлом», де файлові дескриптори надають єдиний інтерфейс для файлів, каналів і пристроїв.
6. **Які descriptors отримує child після `fork()`?** Копію таблиці дескрипторів батька, включно з обома кінцями каналу.
7. **Чому потрібно закривати unused pipe ends?** Щоб уникнути витоку дескрипторів і забезпечити отримання `EOF` читачем після завершення запису.
8. **Коли `read()` із pipe повертає EOF (`0`)?** Коли буфер каналу порожній **і** всі дескриптори кінця запису (`write end`) закриті в усіх процесах.
9. **Що може статися, якщо parent залишить write end відкритим?** Читач назавжди заблокується у `read()` і ніколи не отримає `EOF`.
10. **Що робить `dup2(oldfd, newfd)`?** Атомарно закриває `newfd` і змушує його посилатися на той самий відкритий файл/канал у ядрі, що й `oldfd`.
11. **Як реалізується `>`?** У дитині перед `exec()` відкривається файл (`open`), `STDOUT_FILENO` (`1`) перенаправляється через `dup2(fd, 1)`, тимчасовий `fd` закривається.
12. **Чому program не повинна знати, що її stdout redirected?** Програма пише у стандартний дескриптор `1`, а підміну ресурсу за цим номером виконує оболонка до `exec()`.
13. **Як побудувати `program1 | program2`?** Створити `pipe()`, виконати два `fork()`, у першому перенаправити `stdout` у канал, у другому `stdin` на читання з каналу, закрити зайві кінці та викликати `execvp()`.
14. **Який descriptor першої program підключити до pipe?** `1` (`STDOUT_FILENO`) до кінця запису каналу.
15. **Який descriptor другої program підключити до pipe?** `0` (`STDIN_FILENO`) до кінця читання каналу.
16. **Що таке signal?** Асинхронне програмне переривання, яким ядро або процес сповіщає інший процес про подію.
17. **Чим signal відрізняється від pipe?** `Pipe` передає потік байтів даних, а `signal` — лише номер події асинхронно.
18. **Що робить `kill()`?** Надсилає вказаний сигнал процесу або групі процесів за `PID`.
19. **Чим `SIGTERM` відрізняється від `SIGKILL`?** `SIGTERM` можна перехопити або ігнорувати для коректного завершення, тоді як `SIGKILL` обробляється безпосередньо ядром і безумовно знищує процес.
20. **Чому не можна catch `SIGKILL`?** Це гарантія операційної системи, яка дозволяє ядру або адміністратору завжди примусово завершити будь-який завислий процес.
21. **Що таке `SIGINT`?** Сигнал переривання (`Interrupt`), який драйвер термінала надсилає активній групі процесів при натисканні `Ctrl+C`.
22. **Чому `printf()` не є хорошим загальним вибором для signal handler?** `printf()` використовує внутрішні буфери та м'ютекси `stdio`; якщо сигнал перерве програму під час іншого `printf()`, виникне deadlock або пошкодження пам'яті.
23. **Що таке async-signal-safe function?** Функція, яку безпечно викликати в обробнику сигналів без ризику гонитви чи взаємного блокування незалежно від моменту переривання програми.
24. **Чому shell є user-space program, а не частиною kernel?** Це забезпечує модульність, безпеку та можливість змінювати командні оболонки без модифікації ядра ОС.
25. **Що робить `fork()` у shell?** Створює копію процесу оболонки для налаштування перенаправлень та запуску нової програми без втрати самого `shell`.
26. **Що робить `exec()`?** Замінює адресний простір поточного процесу новим виконуваним файлом, зберігаючи PID та таблицю відкритих дескрипторів.
27. **Для чого потрібен `waitpid()`?** Змушує оболонку чекати завершення дочірнього процесу перед виведенням наступного запрошення `myshell> ` та запобігає появі процесів-зомбі.
28. **Чому `cd` повинен бути shell built-in?** Бо `chdir()` змінює робочий каталог лише поточного процесу; виклик у дочірньому процесі не вплине на батьківський `shell`.
29. **Чому `exit` повинен виконуватися самим shell?** Бо виклик `exit()` у дочірньому процесі завершить лише дитину, а не головний цикл оболонки.
30. **Чому `system()` не підходить для цієї лабораторної?** `system()` передає команду системному `/bin/sh`, приховуючи реальну роботу з `fork()`, `exec()`, `pipe()`, `dup2()` та сигналами.
31. **Що відбувається з file descriptors після `exec()`?** Усі відкриті дескриптори залишаються відкритими та вказують на ті самі ресурси (без прапорця `FD_CLOEXEC`), завдяки чому працюють `>` та `|`.
32. **Як `fork()`, `pipe()` та `dup2()` разом створюють pipeline?** `pipe()` створює канал у ядрі, `fork()` клонує процеси з доступом до нього, а `dup2()` підміняє `stdout` першого і `stdin` другого процесу на кінці каналу перед `exec()`.
33. **Чому pipeline processes можуть виконуватися concurrently?** Обидва дочірні процеси плануються ядром незалежно: поки перший пише у буфер каналу, другий може паралельно читати з нього на іншому ядрі CPU.
34. **Що відбувається, якщо reader pipe завершився, а writer продовжує писати?** Ядро надсилає писачу сигнал `SIGPIPE`, або `write()` повертає `-1` із помилкою `EPIPE`, якщо `SIGPIPE` ігнорується.
35. **Які ресурси повинен закривати parent після створення pipeline?** Батьківський процес обов'язково повинен закрити обидва кінці каналу (`pipefd` і `pipefd`) перед викликом `waitpid()`.

---

## 7. Висновок
У фінальній лабораторній роботі курсу було об'єднано всі ключові системні механізми UNIX/Linux: керування процесами (`fork`, `execvp`, `waitpid`), таблицю файлових дескрипторів і перенаправлення (`open`, `dup2`, `close`), міжпроцесну взаємодію через анонімні канали (`pipe`) та обробку сигналів (`sigaction`, `SIGINT`, `SIGTERM`, `SIGKILL`). Реалізований `mini_shell.c` наочно показав, як командна оболонка комбінує базові системні виклики ядра для запуску програм, перенаправлення виводу та побудови конвеєрів.
