## 1. Program vs Process та декілька інстансів (`process_info.c`)

- **Executable vs Process:** `process_info` до запуску є звичайним пасивним ELF-файлом на диску. Після запуску ОС завантажує його в пам'ять і створює активний **process** із власним унікальним ідентифікатором **PID** та батьківським **PPID** (оболонка `bash`).
- **Один executable — три різні процеси:**

| Instance | PID | PPID | Пояснення |
| :--- | :---: | :---: | :--- |
| **Process 1** | `4217` | `3950` | Перший незалежний запуск `./process_info` |
| **Process 2** | `4229` | `3950` | Другий запуск тієї самої програми (окремий адресний простір і PID) |
| **Process 3** | `4241` | `3950` | Третій запуск (спільний батьківський процес `bash`, але власний стан виконання) |

> **Висновок:** *Program* — це статичний виконуваний файл з інструкціями на диску, а *Process* — це динамічний екземпляр програми під час виконання в пам'яті з власними ресурсами, станом регістрів і PID.

## 2. Спостереження через `/proc/PID`

| Інформація | Джерело у `/proc` | Результат |
| :--- | :--- | :--- |
| **Process name** | `/proc/PID/status` (`Name:`) | `process_info` |
| **PID / PPID** | `/proc/PID/status` (`Pid:` / `PPid:`) | `4217` / `3950` |
| **State** | `/proc/PID/status` (`State:`) | `S (sleeping)` (очікування завершення `sleep(30)`) |
| **Executable** | `readlink /proc/PID/exe` | `/workspaces/EOM-SYSTEMS-COURS/labs/lab04-processes/process_info` |

- `/proc/PID` — це не сам процес, а віртуальний інтерфейс ядра Linux, який відображає внутрішні структури даних процесу в реальному часі. Коли процес завершується, відповідний каталог `/proc/PID` автоматично зникає.

## 3. System Calls та `strace` (`hello.c`, `output.c`)

```text
printf() [C Library + buffering] ──▶ write() [System Call] ──▶ Kernel ──▶ stdout (fd = 1)
```

- **Приклад перехоплення `strace -e write ./output`:**
  ```text
  write(1, "Output using printf\n", 20) = 20
  write(1, "Output using write\n", 19)  = 19
  ```
- **Різниця між `printf()` та `write()`:** `printf()` — це функція стандартної бібліотеки C (user space), яка форматує рядок і використовує буферизацію для зменшення кількості звернень до ядра. `write()` — це прямий системний виклик (system call), який негайно передає керування ядру ОС для запису байтів у файловий дескриптор `1` (`stdout`).

## 4. Створення процесів за допомогою `fork()` (`fork_basic.c`, `fork_memory.c`)

```text
             Process (PID = 5100)
                      │
                    fork()
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
   Parent (PID = 5100)     Child (PID = 5101)
   fork() returns 5101     fork() returns 0
   PPID = bash             PPID = 5100
```

- **Чому `fork()` повертає різні значення?** У `parent` повертається PID новоствореного `child` (`> 0`), щоб батьківський процес міг відстежувати його або викликати `waitpid()`. У `child` повертається `0`, сигналізуючи, що це дочірній процес (свій PPID він завжди може дізнатися через `getppid()`).
- **Порядок виконання:** Не детермінований — після `fork()` обидва процеси стають незалежними планованими одиницями, і порядок виводу визначається планувальником ОС (*scheduler*).
- **Незалежність пам'яті (`fork_memory.c`):** До `fork()` змінна `value = 100`. Після `fork()` батько змінює `value = 300`, а нащадок — `value = 200`. Хоча `&value` виводить **однакову віртуальну адресу** (наприклад, `0x55a8...`) в обох процесах, кожен процес має ізольований віртуальний адресний простір (механізм *Copy-on-Write*), тому зміни одного процесу не впливають на інший.

## 5. Синхронізація `wait()` та Exit Status (`wait_basic.c`)

- Під час `wait(&status)` батьківський процес переводиться у стан очікування (*sleeping/waiting*) і не витрачає процесорний час, доки дочірній процес не завершиться.
- Значення **`42`**, яке повернув `child` (`return 42;`), — це його **exit status** (код завершення), а не PID.
- Макрос `WIFEXITED(status)` перевіряє, чи завершився дочірній процес нормально (через `return` або `exit`), а `WEXITSTATUS(status)` витягує з упакованого числа `status` сам код завершення (`42`).

## 6. Заміна образу програми через `exec()` (`exec_basic.c`, `fork_exec.c`, `launcher.c`)

```text
Parent ──▶ fork() ──▶ Child ──▶ exec() [заміна коду програми при тому ж PID] ──▶ exit() ──▶ Parent wait()
```

- **Головна властивість `exec()`:** На відміну від `fork()`, виклик `exec()` **не створює новий процес** — він повністю замінює код, дані, стек і купу поточного процесу новою програмою (`echo`, `date`, `whoami`). **PID процесу залишається незмінним** (`Before exec PID == After exec PID`).
- Код після `execlp()` (наприклад, `perror`) виконується лише тоді, коли запуск нової програми завершився помилкою.
- Поєднання `fork() → exec() → wait()` у `launcher.c` і `process_runner.c` є базовим механізмом роботи будь-якого командного інтерпретатора (*shell*).

## 7. Стани процесів та Zombie Process (`states.c`, `zombie.c`)

- **Стани процесу (`states.c`):** Під час `sleep(60)` процес перебуває у стані **`S` (Interruptible Sleep / Waiting)** і не використовує CPU, оскільки планувальник ОС знімає його з виконання до спрацювання таймера.
- **Zombie Process (`zombie.c`):** Коли `child` завершується раніше за `parent`, а `parent` ще не викликав `wait()`, процес-нащадок переходить у стан **`Z` (Zombie / defunct)**. Він уже не виконує інструкцій і не займає пам'ять, але його запис у таблиці процесів ядра зберігається, щоб батько міг прочитати його *exit status*. Після виклику `wait()` запис зомбі остаточно видаляється.

## 8. Дерево процесів для двох послідовних `fork()`

```text
        P0 (початковий процес)
       /  \
     P0    P1        ◄── після 1-го fork() (2 процеси)
    / \   / \
  P0  P2 P1  P3      ◄── після 2-го fork() (4 процеси)
```
Виклик `printf()` виконається **4 рази** (загальна формула для `n` послідовних `fork()`: $2^n$).

## 9. Аналіз `process_runner.c` через `strace -f -e trace=process`

Три ключові етапи життєвого циклу на рівні системних викликів ядра Linux:
1. **Створення процесу (`fork()`):**
   ```text
   clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, ...) = 19638
   ```
2. **Запуск нового образу програми (`execvp()`):**
   ```text
   [pid 19638] execve("/usr/bin/date", ["date"], 0x7ffd... /* vars */) = 0
   ```
3. **Очікування та завершення дочірнього процесу (`waitpid()` / `exit_group()`):**
   ```text
   wait4(19638, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 19638
   ```

## 10. Відповіді на контрольні питання

<details>
<summary><b>Натисніть, щоб розгорнути відповіді на всі 24 контрольні питання</b></summary>

1. **Чим program відрізняється від process?** *Program* — пасивний виконуваний файл на диску; *process* — активний екземпляр програми під час виконання в пам'яті зі своїм PID та адресним простором.
2. **Що таке PID?** *Process ID* — унікальний числовий ідентифікатор активного процесу в ОС.
3. **Що таке PPID?** *Parent Process ID* — ідентифікатор батьківського процесу, який створив поточний процес.
4. **Чому один executable може мати декілька PID?** Бо одну й ту саму програму можна запустити кілька разів одночасно; кожен запуск створює окремий ізольований процес зі своїм PID.
5. **Яку роль виконує `/proc/PID`?** Це віртуальна файлова система ядра Linux, яка надає доступ до параметрів, стану, пам'яті та дескрипторів конкретного процесу.
6. **Що таке system call?** Інтерфейс звернення програми з простору користувача (*user space*) до ядра операційної системи (*kernel space*) для виконання привілейованих операцій (ввід-вивід, створення процесів).
7. **Чим function call відрізняється від system call?** *Function call* виконується повністю в межах адресного простору програми без перемикання режиму процесора, тоді як *system call* перемикає CPU у привілейований режим ядра.
8. **Яку роль виконує `strace`?** Утиліта трасування, яка перехоплює та виводить усі системні виклики процесу та отримані ним сигнали.
9. **Що робить `fork()`?** Створює точну копію (клона) поточного процесу — дочірній процес (*child*).
10. **Скільки processes існує після одного успішного `fork()`?** Два процеси: батьківський (*parent*) і дочірній (*child*).
11. **Чому `fork()` повертає 0 у child?** Щоб дочірній процес міг програмно відрізнити себе від батька і піти власною гілкою виконання (`if (pid == 0)`).
12. **Що отримує parent як результат `fork()`?** PID щойно створеного дочірнього процесу (або `-1` у разі помилки).
Используйте код с осторожностью.
13. Чи мають parent і child одну спільну змінну value після fork()? Ні, після fork() кожен процес має власну незалежну копію змінної.
14. Чому однакові virtual addresses у parent та child не означають спільну змінювану пам'ять? Бо кожен процес має власну таблицю сторінок (page table), яка відображає однакові віртуальні адреси на різні фізичні сторінки RAM (механізм Copy-on-Write).
15. Що робить exec()? Завантажує нову програму в адресний простір поточного процесу, повністю замінюючи його старий код і дані.
16. Чи створює exec() новий process? Ні, він лише замінює програму всередині вже існуючого процесу.
17. Що відбувається з PID після успішного exec()? PID залишається тим самим.
18. Для чого потрібен wait()? Призупиняє батьківський процес до завершення дочірнього, дозволяє отримати його exit status і звільняє запис про нащадка з таблиці процесів (запобігаючи появі зомбі).
19. Що таке exit status? Цілочисельний код (0–255), який процес передає ядру при завершенні (0 означає успіх, ненульове значення — код помилки).
20. Що таке zombie process? Процес, який уже завершив виконання, але його запис залишається в таблиці процесів ядра, оскільки батьківський процес ще не прочитав його статус через wait().
21. Чи zombie продовжує виконувати instructions? Ні, його код уже завершено, а пам'ять звільнено.
22. У чому різниця між Ready, Running та Waiting? Running — процес прямо зараз виконується на ядрі CPU; Ready — готовий до роботи і чекає своєї черги у планувальника; Waiting — заблокований в очікуванні події (таймера sleep, вводу-виводу або wait).
23. Чому порядок виконання parent та child після fork() не можна просто гарантувати? Бо вибір того, який процес отримає процесорний час першим, залежить від алгоритму планувальника ядра ОС та поточного навантаження системи.
24. Як fork → exec → wait пов'язаний із роботою shell? Коли користувач вводить команду в терміналі, shell викликає fork(), у дочірньому процесі підміняє себе на цю команду через exec(), а в батьківському викликає wait(), чекаючи завершення команди перед показом нового запрошення.
