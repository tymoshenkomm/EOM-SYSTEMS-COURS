```text
Source (.c) ──▶ Preprocessor (.i) ──▶ Compiler (.s) ──▶ Assembler (.o) ──▶ Linker (ELF) ──▶ Loader / OS ──▶ Process Memory
```

## 1. Етапи Build Pipeline (`program.c` та `memory_map.c`)

| Файл | Етап побудови | Що містить | Чи може CPU виконати безпосередньо? |
| :--- | :--- | :--- | :---: |
| **`.c`** | Source Code | Вихідний текст програми мовою C із директивами препроцесора (`#include`) | ❌ Ні |
| **`.i`** | Preprocessing (`gcc -E`) | Розгорнутий код C без коментарів, із підставленим вмістом `<stdio.h>` (~700+ рядків) | ❌ Ні |
| **`.s`** | Compilation (`gcc -S`) | Інструкції мовою Assembly (Intel syntax) для архітектури x86-64 | ❌ Ні |
| **`.o`** | Assembly (`gcc -c`) | Relocatable object file (машинний код функцій, але без прив'язки зовнішніх бібліотек) | ❌ Ні |
| **`executable`** | Linking (`gcc`) | Готовий виконуваний файл формату **ELF64** із вирішеними адресами та секціями | ✅ Так |

## 2. Помилка лінкера (`undefined reference`) та її виправлення (`main.c` + `calculate.c`)

- **Експеримент:** При компіляції `gcc -c main.c -o main.o` помилок не виникає, оскільки компілятору достатньо прототипу `int calculate(int a, int b);`. Проте спроба зібрати програму командою `gcc main.o -o app` завершується помилкою **`undefined reference to 'calculate'`**.
- **Причина:** У `main.o` символ `calculate` позначений як `U` (*Undefined*). Компілятор лише перевіряє синтаксис і типи, а пошук реалізації функції та з'єднання файлів виконує **linker**.
- **Виправлення:** Після компіляції `calculate.c` у `calculate.o` (де символ `calculate` має статус `T` — визначений у `.text`) спільна лінковка `gcc main.o calculate.o -o app` успішно об'єднує обидва object-файли в робочий додаток (`30`).

## 3. Аналіз структури ELF (`readelf -h program`)

| Властивість ELF | Значення у середовищі | Пояснення |
| :--- | :--- | :--- |
| **Class** | `ELF64` | 64-бітний формат виконуваного файлу Linux |
| **Data** | `2's complement, little endian` | Доповняльний код для від'ємних чисел і порядок байтів Little-endian |
| **Type** | `DYN (Position-Independent Executable file)` | Виконуваний файл із підтримкою рандомізації адрес (PIE / ASLR) |
| **Machine** | `Advanced Micro Devices X86-64` | Цільова процесорна архітектура x86-64 |
| **Entry point** | `0x1060` | Віртуальна адреса стартової точки запуску програми (`_start`) |

## 4. Секції ELF (`readelf -S`, `nm`, `objdump` — `sections.c`)

| Секція | Призначення | Приклади об'єктів із програми (`sections.c` / `program.c`) |
| :--- | :--- | :--- |
| **`.text`** | Виконуваний машинний код інструкцій (тільки читання та виконання) | Функції `main()`, `add()` |
| **`.rodata`** | Константи та рядкові літерали (тільки читання) | `const char message[] = "Computer Systems"`, рядок формату `"Result: %d\n"` |
| **`.data`** | Ініціалізовані глобальні та `static` змінні (читання/запис) | `int initialized = 123`, `static int static_initialized = 456`, `int global_value = 10` |
| **`.bss`** | Неініціалізовані (або обнулені) глобальні та `static` змінні | `int uninitialized`, `static int static_uninitialized`, `int global_empty` |

---

## 5. Експеримент із великою секцією `.bss` (`size sections`)

При заміні `int uninitialized;` на масив `int large_array;` (`400 000` байтів):

| Варіант програми | `text` (bytes) | `data` (bytes) | `bss` (bytes) | Розмір файлу на диску (`ls -lh`) |
| :--- | :---: | :---: | :---: | :---: |
| **До зміни** (`int uninitialized;`) | `1450` | `608` | `16` | ~16 KB |
| **Після зміни** (`int large_array;`) | `1450` | `608` | `400032` | ~16 KB |

> **Висновок:** Секція `.bss` не зберігає нулі фізично у виконуваному файлі на диску — у заголовку ELF записується лише її необхідний розмір (`400 032` байти). Операційна система виділяє та обнуляє цю пам'ять у RAM лише під час запуску процесу.

## 6. Динамічні бібліотеки (`ldd program`)

Команда `ldd program` показує залежність від стандартної бібліотеки C:
```text
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
```
- **Чи міститься код `printf()` всередині `program`?** Ні, у виконуваному файлі є лише посилання на зовнішній символ `printf@GLIBC`.
- **Що означає `.so`?** *Shared Object* — динамічна бібліотека (аналог `.dll` у Windows).
- **Перевага:** Код бібліотеки завантажується в оперативну пам'ять один раз і спільно використовується десятками процесів, що суттєво економить місце на диску та RAM і дозволяє оновлювати бібліотеки без перекомпіляції програм.

## 7. Executable vs Process (`process.c`)

- **`process` (Executable file):** Пасивний файл на диску, що містить машинний код, метадані ELF та початкові дані.
- **`PID` (Running process):** Активний екземпляр програми, завантажений ОС у пам'ять із власним віртуальним адресним простором, стеком, купою, відкритими дескрипторами та станом регістрів CPU.

## 8. Розміщення змінних у пам'яті та ASLR (`memory.c`)

### Прогноз і фактичні результати

| Об'єкт | Очікувана область | Фактична адреса (приклад запуску) | Підтвердження |
| :--- | :---: | :---: | :---: |
| `main` | `code` (`.text`) | `0x5b94822e9189` | Найнижчі адреси сегмента коду |
| `global_initialized` / `static_initialized` | `data` (`.data`) | `0x5b94822ec010` / `0x5b94822ec014` | Поруч у сегменті ініціалізованих даних |
| `global_uninitialized` / `static_uninitialized` | `bss` (`.bss`) | `0x5b94822ec01c` / `0x5b94822ec020` | Одразу після `.data` у сегменті даних |
| `dynamic` (`malloc`) | `heap` | `0x5b94baa102a0` | Окрема область динамічної пам'яті вище `.bss` |
| `local` | `stack` | `0x7ffd03af6ddc` | Найвищі адреси користувацького простору |

- **Вплив ASLR:** При кожному повторному запуску `./memory` базові адреси змінюються. Це робота механізму безпеки **ASLR** (*Address Space Layout Randomization*), який випадковим чином зміщує області пам'яті для захисту від експлойтів.

## 9. Експерименти зі Stack (`stack.c`) та Heap (`heap.c`)

- **Stack (`stack.c`):** При вкладених викликах `level1() → level2() → level3()` адреси локальних змінних (`&a` → `&b` → `&c`) **зменшуються** (наприклад, на 32 байти на кожен фрейм). Це відповідає архітектурі x86-64, де стек росте вниз (від старших адрес до молодших).
- **Heap (`heap.c`):** Три послідовні виклики `malloc(sizeof(int))` повертають адреси в області кучі з кроком у 32 байти (через службові заголовки блоків алокатора та вирівнювання пам'яті). На відміну від стеку, об'єкти в кучі живуть до явного виклику `free()`.

## 11. Відповіді на контрольні питання

<details>
<summary><b>Натисніть, щоб розгорнути відповіді на всі 22 контрольні питання</b></summary>

1. **Які основні етапи проходить C-програма до створення executable?** Preprocessing (`-E`) → Compilation (`-S`) → Assembly (`-c`) → Linking.
2. **Що робить preprocessor?** Видаляє коментарі, розкриває макроси (`#define`) та вставляє вміст заголовкових файлів (`#include`), створюючи `.i` файл.
3. **Що створює compiler?** Перекладає очищений код C у текстовий файл мовою Assembly (`.s`) для конкретної процесорної архітектури.
4. **Що робить assembler?** Перетворює текстові мнемоніки Assembly у двійковий машинний код, формуючи об'єктний файл (`.o`).
5. **Що містить object file?** Машинний код функцій, дані та таблицю символів (як визначених, так і зовнішніх невизначених посилань).
6. **Навіщо потрібен linker?** Об'єднує кілька `.o` файлів, підключає системні бібліотеки, розв'язує зовнішні посилання (`undefined references`) та формує єдиний ELF executable.
7. **Що означає `undefined reference`?** Помилка лінкера, яка виникає, коли функція або змінна оголошена (використовується), але її реальна реалізація відсутня в усіх переданих файлах і бібліотеках.
8. **Що таке symbol?** Іменований ідентифікатор функції або глобальної/статичної змінної у таблиці символів об'єктного чи виконуваного файлу.
9. Чим header file відрізняється від library? Header file (.h) містить лише оголошення (прототипи функцій, типи, макроси) для компілятора, а library (.so / .a) — вже скомпільований машинний код реалізації для лінкера.
10. Що таке ELF? Executable and Linkable Format — стандартний формат виконуваних файлів, об'єктного коду та спільних бібліотек у Linux.
11. Що зазвичай містить .text? Скомпільовані машинні інструкції програми (сегмент коду).
12. Що зазвичай містить .rodata? Незмінні дані (Read-Only Data): рядкові літерали та const-змінні.
13. У чому різниця між .data та .bss? У .data зберігаються глобальні та статичні змінні з початковим ненульовим значенням (вони фізично записані у файл), а в .bss — неініціалізовані або нульові змінні.
14. Чому велика .bss не обов’язково означає такий самий приріст розміру executable? Оскільки всі змінні у .bss за замовчуванням дорівнюють нулю, у файлі на диску зберігається лише їхній загальний розмір, а реальна пам'ять виділяється ОС при старті процесу.
15. Що показує ldd? Список динамічних спільних бібліотек (.so), необхідних для запуску виконуваного файлу, та шляхи до них.
16. Чим executable відрізняється від process? Executable — це статичний файл на диску, а process — це активна програма під час виконання в оперативній пам'яті з власним PID і ресурсами.
17. Де концептуально розташовуються local variables? У стеку (Stack) всередині стекового фрейму поточної функції.
18. Для чого використовується heap? Для динамічного виділення пам'яті під час виконання програми (malloc, calloc, realloc), коли розмір даних заздалегідь невідомий або дані мають пережити вихід із функції.
19. Яка різниця між stack та heap? Stack керується автоматично (LIFO), працює дуже швидко, має обмежений розмір і росте вниз; heap керується вручну програмістом (malloc/free), має значно більший обсяг, але виділення відбувається повільніше.
20. Чому адреси можуть змінюватися між запусками програми? Через технологію ASLR (Address Space Layout Randomization), яка випадково зміщує базові адреси сегментів пам'яті для захисту від атак.
21. Що таке temporal locality? Часова локальність — принцип, згідно з яким якщо програма звернулася до певної комірки пам'яті, з високою ймовірністю вона звернеться до неї знову найближчим часом (наприклад, змінна лічильника в циклі).
22. Що таке spatial locality? Просторова локальність — принцип, згідно з яким якщо програма звернулася до певної адреси пам'яті, найближчим часом вона звернеться до сусідніх адрес (наприклад, послідовний прохід по елементах масиву).

12. Висновок

Під час виконання лабораторної роботи було детально простежено всі етапи побудови програми мовою C — від розгортання препроцесором директиви #include до формування ELF64-файлу лінкером. На практиці перевірено будову секцій .text, .rodata, .data та .bss, доведено відсутність фізичного місця під нулі .bss на диску, досліджено роботу динамічної лінковки (libc.so.6) та підтверджено розподіл пам'яті процесу між кодом, глобальними даними, купою (heap), стеком (stack) і дію механізму захисту ASLR.
