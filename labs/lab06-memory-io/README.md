# Лабораторна робота №6. Віртуальна пам'ять, File Descriptors та I/O

## 1. Мета роботи
Дослідити дві фундаментальні абстракції, які операційна система надає процесу: **віртуальний адресний простір** (розташування сегментів пам'яті, `/proc/<PID>/maps`, розмір сторінки, ліниве виділення фізичної пам'яті `VmSize`/`VmRSS`, захист пам'яті та `SIGSEGV`) та **файлові дескриптори / системний ввід-вивід** (`stdin`/`stdout`/`stderr`, `open`, `read`, `write`, `close`, `lseek`, буферизація `stdio` проти `POSIX I/O`, аналіз системних викликів через `strace` та реалізація копіювання файлів `file_copy.c`).

**Аналіз адрес:**
1. **Які адреси розташовані близько одна до одної?** Адреси `function`, `global_initialized`, `global_uninitialized` та `static` розташовані поруч у нижній частині адресного простору, оскільки всі вони є частинами завантаженого ELF-файлу (сегменти `.text`, `.data`, `.bss`).
2. **Чи схожа адреса `heap` на адреси глобальних змінних?** Вона знаходиться вище за статичні сегменти даних (у зоні динамічної купи `[heap]`, яка зростає вгору).
3. **Чи знаходиться `stack` в іншій області?** Так, `stack` розташований у значно вищій ділянці віртуального адресного простору (`0x7ff...`) і зростає вниз.
4. **Чи однакові адреси між різними запусками?** Ні, через механізм **ASLR (Address Space Layout Randomization)** ядро Linux при кожному запуску випадково зміщує базові адреси сегментів коду, купи та стеку для захисту від експлойтів.

### Завдання 4. Heap складається з Virtual Memory (`heap_growth.c`)
Стан пам'яті процесу в `/proc/<PID>/status` до та після запису в кожну сторінку виділених 100 МБ:
```text
B: ['VmSize:\t  105092 kB', 'VmRSS:\t    1716 kB']
A: ['VmSize:\t  105092 kB', 'VmRSS:\t  104112 kB']
```
**Висновок:** Після виклику `malloc(100 MB)` збільшується віртуальний розмір процесу (`VmSize`), проте фізична пам'ять (`VmRSS`) майже не витрачається (ліниве виділення — *lazy allocation* / *demand paging*). Лише коли програма реально звертається до кожної сторінки (`memory[i] = 1`), виникають *minor page faults*, і ядро виділяє реальні фізичні фрейми RAM, що різко збільшує `VmRSS`.

### Завдання 14, 15 та 16. Redirection (`streams.c`) та Buffering (`buffering.c`)


- Оператор `>` перенаправляє лише дескриптор `1` (`stdout`) у файл `normal.txt` (`Normal output`), тоді як дескриптор `2` (`stderr`) залишається прив'язаним до термінала (`Error output`). Сама програма не знає про перенавлення і продовжує писати у `fd 1`.

- Без `fflush(stdout)` виклики `printf("A")`, `printf("B")`, `printf("C")` накопичують символи у буфері бібліотеки `stdio` (у просторі користувача), тому системний виклик `write(1, "D", 1)` виконується першим, а буфер `stdio` скидається лише при завершенні `main()` (у результаті виводиться `DABC`).


**Перевірка копіювання текстового та бінарного файлів і трасування `strace`:**

- Той самий цикл `read()`/`write()` однаково копіює і текстові файли, і скомпільовані бінарні виконувані файли (`cmp` повертає `0`), оскільки на рівні системних викликів ОС будь-який файл — це просто послідовність байтів.
- Внутрішній цикл `while (total_written < bytes_read)` гарантує коректну обробку **partial writes**, якщо `write()` за один виклик записав менше байтів, ніж було прочитано.

**Повна схема Data Path (від джерела до приймача через віртуальну пам'ять та ядро):**
```text
SOURCE FILE
     │
     │ read(src, buf, 4096)
     ▼
══════════════════════
     Kernel (VFS / Page Cache)
══════════════════════
     │  копіювання у user-space буфер (перевірка virtual address через MMU)
     ▼
Process Virtual Memory
     │
     │ char buf (Stack)
     │
     ▼
══════════════════════
     Kernel (VFS / Page Cache)
══════════════════════
     │  write(dst, buf, bytes_read)
     ▼
DESTINATION FILE
```

**Інтеграційне пояснення (`read(fd, buffer, sizeof(buffer))`):**
Процес передає у системний виклик `read()` дескриптор `fd` та **віртуальну адресу** масиву `buffer` на своєму стеку. Перетинаючи межу системного виклику (**System Call Boundary**), керування переходить до **ядра (Kernel)**. Ядро знаходить відкритий файл за номером `fd`, зчитує дані з файлової системи та копіює їх у буфер процесу; при цьому **MMU** та таблиця сторінок транслюють віртуальні адреси сторінок (`pages`) буфера у фізичні кадри RAM та перевіряють права доступу (`rw-`).

## 4. Відповіді на контрольні питання

1. **Що таке virtual address?** Логічна адреса у віртуальному адресному просторі процесу, яку використовує програма і яка транслюється у фізичну адресу за допомогою MMU.
2. **Чим virtual address відрізняється від physical address?** Віртуальна адреса існує лише в межах адресного простору конкретного процесу, тоді як фізична адреса вказує на реальну комірку оперативної пам'яті (RAM).
3. **Що таке virtual address space?** Ізольований діапазон віртуальних адрес, який операційна система надає кожному процесу.
4. **Чому два processes можуть використовувати однакову virtual address?** Тому що кожен процес має власну таблицю сторінок (`page table`), і MMU відображає однакові віртуальні адреси різних процесів у різні фізичні кадри RAM.
5. **Що таке page?** Блок віртуальної пам'яті фіксованого розміру (у нашій системі — `4096` байтів), який є базовою одиницею відображення віртуальної пам'яті.
6. **Що таке page frame?** Блок фізичної оперативної пам'яті (RAM) такого ж розміру (`4096` байтів), у який завантажується віртуальна сторінка.
7. **Що таке page table?** Структура даних у пам'яті ядра ОС, що зберігає відповідність між номерами віртуальних сторінок процесу та номерами фізичних кадрів, а також біти прав доступу.
8. **Яку роль виконує MMU?** *Memory Management Unit* — апаратний блок процесора, який на льоту перекладає віртуальні адреси у фізичні та перевіряє права доступу (`r`, `w`, `x`).
9. **Що таке TLB?** *Translation Lookaside Buffer* — швидкий апаратний кеш всередині MMU, що зберігає нещодавні трансляції віртуальних сторінок у фізичні кадри.
10. **Чим TLB miss відрізняється від page fault?** При *TLB miss* трансляції немає в кеші TLB, але сторінка є у RAM, і апаратура просто підвантажує запис із `page table`. При *page fault* сторінка взагалі відсутня у RAM або порушено права доступу, що викликає переривання і передачу керування ядру ОС.
11. **Що таке page fault?** Виняток (переривання) процесора при зверненні до віртуальної сторінки, яка не відображена у фізичну пам'ять або недоступна для даної операції.
12. **Чи page fault завжди означає помилку програми?** Ні. *Minor/major page faults* є нормальним механізмом ОС (наприклад, ліниве виділення пам'яті при першому записі після `malloc()` або підвантаження сторінок із диска). Помилкою (`SIGSEGV`) є лише звернення до невалідної чи захищеної адреси.
13. **Як virtual memory допомагає ізолювати processes?** Кожен процес бачить лише сторінки, внесені до його власної таблиці сторінок, і фізично не може звернутися до кадрів пам'яті іншого процесу або ядра.
14. **Що означають `r`, `w`, `x` у memory mappings?** Права доступу до регіону пам'яті: `r` (read) — читання, `w` (write) — запис, `x` (execute) — виконання машинних інструкцій.
15. **Чому code не обов'язково повинен бути writable?** Заборона запису (`r-x`) у сегмент коду захищає програму від випадкового перезапису інструкцій та ускладнює атаки впровадження шкідливого коду (принцип *W^X*).
16. **Чому `malloc()` не слід просто ототожнювати з негайним використанням такої ж кількості physical RAM?** Через *demand paging* (ліниве виділення): `malloc()` резервує лише діапазон віртуальних адрес (`VmSize`), а фізичні кадри (`VmRSS`) виділяються ядром лише в момент фактичного звернення до сторінок.
17. **Що таке file descriptor?** Невід'ємне ціле число, яке ідентифікує відкритий файл, канал або пристрій у таблиці відкритих файлів процесу.
18. **Чим pathname відрізняється від file descriptor?** `Pathname` — це текстовий шлях до файла у файловій системі, а `file descriptor` — числовий дескриптор відкритого ресурсу в ядрі після виклику `open()`.
19. **Що зазвичай представляють descriptors `0`, `1`, `2`?** `0` — стандартний ввід (`stdin`), `1` — стандартний вивід (`stdout`), `2` — стандартний потік помилок (`stderr`).
20. **Що робить `open()`?** Відкриває або створює файл за вказаним шляхом і повертає найменший вільний файловий дескриптор.
21. **Що повертає `read()`?** Кількість фактично прочитаних байтів (`> 0`), `0` при досягненні кінця файла (EOF) або `-1` у разі помилки.
22. **Що означає `read() == 0`?** Досягнуто кінець файла (End of File, EOF) або інший кінець каналу/сокета закрито.
23. **Що повертає `write()`?** Кількість фактично записаних байтів (`>= 0`) або `-1` у разі помилки.
24. **Чому потрібно враховувати partial writes?** Системний виклик `write()` може записати менше байтів, ніж запитано (через переповнення буферів, переривання сигналом чи особливості пристрою), тому потрібно дописувати залишок у циклі.
25. **Що таке file offset?** Поточна позиція (зміщення у байтах від початку файла), з якої відбудеться наступна операція `read()` або `write()`.
26. **Для чого використовується `lseek()`?** Для явної зміни поточного `file offset` відкритого дескриптора (відносно початку, поточної позиції або кінця файла).
27. **Чим `FILE *` відрізняється від file descriptor?** `FILE *` — це високорівнева структура бібліотеки C (`stdio`), яка містить буфер у просторі користувача та обгортає низькорівневий системний `file descriptor` (`int`).
28. **Чому `printf()` не обов'язково негайно викликає `write()`?** Тому що `printf()` накопичує дані у внутрішньому буфері `stdio` і викликає системний `write()` лише при заповненні буфера, зустрічі символу `
` (для термінала), виклику `fflush()` або завершенні програми.
29. **Що таке buffering?** Накопичення даних у проміжній ділянці пам'яті для зменшення кількості дорогих системних викликів `read()`/`write()`.
30. **Що робить `fflush()`?** Примусово скидає вміст буфера `stdio` з простору користувача у ядро ОС через системний виклик `write()`.
31. **Чому redirection `>` може працювати без зміни source code програми?** Оболонка (`shell`) перед запуском програми підміняє ресурс, на який вказує дескриптор `1` (`stdout`), а сама програма продовжує писати у `fd 1`.
32. **Чому `file_copy` може однаково копіювати text та binary files?** На рівні системних викликів `read()`/`write()` усі файли обробляються як неструктуровані потоки байтів без прив'язки до кодування чи символів.
33. **Де фізично/логічно знаходиться `buffer` під час `read()`?** Логічно — у віртуальному адресному просторі процесу (у нашому випадку на стеку функції `main`), фізично — у відповідних кадрах оперативної пам'яті RAM, куди ядро копіює прочитані дані.
34. **Як file descriptor, virtual memory та system call взаємодіють під час I/O?** Програма передає `fd` та віртуальну адресу буфера у системний виклик (`read`/`write`); ядро за `fd` знаходить об'єкт вводу-виводу, а через таблицю сторінок і MMU звертається до буфера у віртуальній пам'яті процесу для передачі даних.

## 5. Висновок
У ході лабораторної роботи було експериментально досліджено дві базові абстракції операційної системи: віртуальну пам'ять процесу та файлові дескриптори POSIX I/O. Проаналізовано розміщення сегментів пам'яті у `/proc/PID/maps`, механізм лінивого виділення сторінок (`VmSize` проти `VmRSS`) та захист пам'яті при зверненні за нульовим вказівником (`SIGSEGV`). На практиці вивчено системні виклики `open()`, `read()`, `write()`, `lseek()` і `close()`, різницю між буферизованим виводом `stdio` та прямим системним I/O, а також реалізовано утиліту `file_copy.c` з коректною обробкою часткового запису (`partial writes`).
